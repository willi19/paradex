GR00T N1.7 finetune on xArm6 + Inspire — status report

Last updated after Phase 7 VRAM probe succeeded on 1× A5000 with paged 8-bit Adam + gradient checkpointing. Phase 8 (real finetune) is the next action. Read top-down.

1. The goal

Finetune nvidia/GR00T-N1.7-3B (a 3B-parameter vision-language-action model) on a custom embodiment: xArm6 6-DOF arm + Inspire right hand performing the task "sweep the cutting board with the broom", using ~30 teleop demonstrations already recorded under /media/ssd1/sungjoo/copy_teleop_test/task/2_broom_sweep/.

Eventual deployment target: closed-loop rollout in Isaac Lab (separate container) with the trained policy served over ZMQ by gr00t/eval/run_gr00t_server.py.

2. Hard constraints (drive every decision)

ConstraintWhyHow it shaped the plan
1–2× RTX A5000 (24 GB); NVIDIA's stated minimum is 40 GB Below the official spec Phase 7 is an explicit VRAM probe before any committed training run. Escalation table: shrink batch → shrink action horizon → gradient checkpointing → FSDP. Plain DDP (torchrun) does NOT lower per-GPU VRAM — only FSDP does.

Small steps, fast fail, no fallbacks Catch problems early; avoid silent corruption Every phase has one verifiable gate. The converter aborts on dimension drift, fps drift, missing files, or >5-frame video-count spread.
Visual output at every step Manual verification beats trusting numbers Wrote scripts/inspect_teleop_episode.py (Phase 1 schema check), converter emits per-episode thumbnails + state/action curves, scripts/review_lerobot_dataset.py does final dataset audit (Phase 5.5).

3. Decisions locked early

Action space12-D joint-space (6 arm joints + 6 Inspire fingers). Chose joint-space over EEF because (a) recorded data is qpos, (b) no IK layer needed at deploy. Action representationRELATIVE for both arm and hand (model predicts deltas from the current state). Goes hand-in-hand with the next-state-as-action choice (see below). Action sourcenext-state-as-action: action[t] = state[t+1]. Sidesteps state vs action frame mismatch entirely. Recorded arm/action_qpos.npy would have needed per-joint offset calibration; trivial-to-train delta loss is preferred. Eval targetIsaac Lab in a separate Docker container. GR00T container runs run_gr00t_server.py; Isaac Lab container runs the scene + ZMQ client. This is the officially supported split — Isaac Sim ships embedded Python that collides with the gr00t venv. Embodiment tagEmbodimentTag.NEW_EMBODIMENT. Custom robots use this tag exclusively; the base 3B checkpoint refuses it (zero-shot disallowed by design — finetune is the only path).

  3. Phase 2 — write & validate converter done

    Tool: scripts/convert_teleop_to_lerobot.py. Three significant code iterations:

    1. Unit mismatch: arm position is rad, arm action is deg. Initial heuristic max(|x|) > π+0.1 was too eager — it flagged the rad position (which legally reads 4.22 rad on the wrist) as degrees and shrank it by 57×. Fixed threshold to 2π + 0.2 ≈ 6.5: rotational joints never exceed ±2π, so any value past that is definitely degrees.
    2. ±180° wraparound: np.unwrap(period=360.0) before deg→rad prevents 356° apparent jumps when a joint crosses the ±180° boundary.
    3. next-state-as-action: --action-source next_state (default) replaces the recorded action stream with state[t+1], last frame repeated. This is what enabled clean training.
    4. Per-camera frame-count drift: cam3 had 896 frames vs others' 897 in one episode. Naive trimming caused ffmpeg to seek past end-of-stream during thumbnail generation. Fix: use min(per-cam nframes) as the master timeline, trim each video to that count, and abort if spread > 5 frames.

    The converter also (a) probes ffmpeg for fps/resolution, (b) interpolates arm + hand state/action onto the video frame grid via np.interp, (c) writes a parquet per episode, (d) remuxes each mp4 (-c copy, ~10× faster than transcoding), (e) writes meta/info.json, episodes.jsonl, tasks.jsonl, modality.json, (f) saves per-episode thumbnail + state/action curve png.

    Converter parquet schema (matches demo_data/cube_to_bowl_5) 
    observation.state : 12-D float32  [arm:0..6, hand:6..12]
action            : 12-D float32  [arm:0..6, hand:6..12]  (= state shifted by 1)
timestamp         : float32
frame_index       : int64
episode_index     : int64
index             : int64  (global, across all episodes)
task_index        : int64  (→ tasks.jsonl)
  4. Phase 3 — modality config + EmbodimentTag done

    New file examples/xarm_inspire/xarm_inspire_config.py — lifted from the SO100 template, registers EmbodimentTag.NEW_EMBODIMENT with the 4 cameras (cam0..cam3), arm + hand state/action, 16-step action horizon, both arm and hand as RELATIVE.

    The dataset's meta/modality.json declares the byte-range slicing (state.arm = [0..6), state.hand = [6..12)), so the same modality config works for any state/hand dim.

  8. Phase 5.5 — manual dataset completeness review done

    Tool: scripts/review_lerobot_dataset.py. Original implementation used ffprobe -count_frames which forces a full decode per video — projected ~20 min for 120 videos. Killed it, patched to read the cheap nb_frames metadata first (instant, falls back to count_frames only if missing).

    Result: FAILURES: (none). Per-episode CSV confirms:

    • Episode lengths range 862 → 1,679 frames (29–56 s @ 30 fps).
    • All 4 per-camera frame counts equal the parquet row count for every episode.
    • state_dim = action_dim = 12 across all 30 episodes.
    • State range is fairly homogeneous: most episodes' state_min ∈ [-1.7, -0.9] rad. Outliers: ep 20, 21, 26, 27 with state_min near -2 to -3 rad; ep 24, 27 near -4.7 to -4.9 rad — consistent with wider wrist excursions. Worth eyeballing the corresponding _review/episode_000024_cam_thumbs.jpg but not a blocker (xArm6 wrist rotates > ±π legally).

    Artifacts in /data/datasets/xarm_inspire_broom_v1/_review/: 30 × episode_NNNNNN_cam_thumbs.jpg + per_episode_stats.csv + state_action_summary.png.

  9. Phase 7 — VRAM probe (1× A5000) done

    Result: first attempt at batch=8, grad-accum=4 with stock optimizer hit CUDA OOM exactly as predicted — model + Adam fp32 state for 1.62 B trainable params is ~26 GB before any activations, ceiling is 24 GB.

    Escalation applied (single try, no flailing):

    • uv pip install bitsandbytes → 0.49.2
    • Patched gr00t/experiment/launch_finetune.py to forward two env vars into the underlying training config: GR00T_OPTIM → config.training.optim, and GR00T_GRAD_CKPT=1 → config.training.gradient_checkpointing.
    • Set GR00T_OPTIM=paged_adamw_8bit (paged 8-bit Adam) and GR00T_GRAD_CKPT=1 (gradient checkpointing).
    • Dropped --global-batch-size from 8 to 4 for additional headroom.

    Result on probe v2 (1× A5000, 20 steps to fail-fast):

    • 20/20 steps completed ✓
    • Wall-clock 6:24 (first step 5:47 was shard-cache warmup; steady-state ~2 s/step)
    • Loss 1.01 → 1.03 — finite, no NaN
    • No OOM

    Math behind the fix:

    Bufferfp32 Adampaged 8-bit Adam + grad-ckpt
    Adam exp_avg + exp_avg_sq for 1.62 B trainable~13 GB~3.25 GB (4× reduction)
    Activationsfull~70 % (recomputed on backward)
    Estimated total at training time~26 GB (won't fit)well under 24 GB

    Defaults in scripts/run_finetune_xarm_inspire.sh now bake these in (GR00T_OPTIM=paged_adamw_8bit GR00T_GRAD_CKPT=1).

  10. Phase 8 — real finetune running — single-GPU (after 2 DDP attempts)

    Two DDP attempts both died at the post-init NCCL barrier (10-min watchdog vs ~10-min stats regen per rank). Switched to single-GPU on GPU 0 — the probe already proved this path. Wall-clock estimate ~75 min for 2000 steps.

    CUDA_VISIBLE_DEVICES=0 NUM_GPUS=1 RUN_NAME=broom_run1 MAX_STEPS=2000 \
  bash /workspace/scripts/run_finetune_xarm_inspire.sh

    Defaults: paged_adamw_8bit, gradient checkpointing, batch 4, grad-accum 4 → effective batch 16. Wandb run live at junesjukim-seoul-national-university/finetune-gr00t-n1d7.
